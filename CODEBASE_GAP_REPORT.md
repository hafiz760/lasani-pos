# RexPOS Codebase Gap Report

**Assessment date:** 2026-06-23  
**Scope:** Electron main process, preload bridge, renderer, Mongoose models, IPC handlers, configuration, package scripts, and repository automation.  
**Method:** Static review of the current working tree. Findings marked **inferred** are based on the absence of an implementation in the reviewed scope and require an operational check before being treated as production fact.

## Executive Summary

RexPOS has broad POS functionality, a sensible Electron-to-MongoDB process boundary, and a now-consistent source formatter. Its main risks are not missing screens: they are **trust boundaries and multi-record consistency**.

The application treats renderer-provided IDs, roles, and store selections as trusted inputs. It also performs stock, payment, customer/supplier balance, account, and transaction updates in separate database operations without a shared transaction boundary. A failed or concurrent operation can therefore leave a sale, inventory, customer balance, and ledger out of sync.

The recommended first milestone is to protect every IPC command with server-side identity and authorization, then make the sale/payment/refund/purchase-order workflows atomic and auditable. Do not add further financial workflows before those controls exist.

| Priority | Gap                                                                                | Primary consequence                                          | Recommended action                                                          |
| -------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| P0       | Main-process IPC does not establish or authorize caller identity                   | Any renderer request can supply another user/store/record ID | Create a main-process session and authorize every IPC command centrally     |
| P0       | Financial and stock workflows are not atomic                                       | Partial failures can corrupt balances, stock, and reports    | Use MongoDB sessions/transactions around domain workflows                   |
| P0       | MongoDB URI can be logged and is persisted as plain JSON                           | Database credentials may be exposed locally or in logs       | Stop URI logging; use OS credential storage or an encrypted secret store    |
| P1       | Accounting entries are single-sided and account balances are not derived centrally | Ledger cannot reliably reconcile to accounts or sales        | Introduce balanced journal entries and a posting service                    |
| P1       | Server-side IPC input validation is inconsistent/absent                            | Malformed or unauthorized payloads reach persistence logic   | Validate every command with shared Zod schemas in the main process          |
| P1       | Audit model exists but is not used by the reviewed workflows                       | Sensitive changes cannot be traced reliably                  | Write immutable audit events in the same transaction as each change         |
| P1       | There is no first-party automated test suite or CI configuration in the repository | Regressions in sales, refunds, and stock are likely          | Add integration tests and a CI quality gate                                 |
| P2       | Preload API has broadly untyped parameters and duplicated API contracts            | Renderer/main IPC changes can silently break at runtime      | Define shared request/response contracts and derive bridge types            |
| P2       | Database configuration has conflicting sources of truth                            | Packaged and configured behavior can diverge                 | Make the configuration manager the sole production URI source               |
| P2       | Electron hardening and file protocol validation need review                        | Renderer compromise has larger local-system impact           | Enable sandboxing where possible and restrict external/file protocol inputs |

## Severity Model

| Level | Meaning                                                           | Target response                                             |
| ----- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| P0    | Security or data-integrity weakness in a core POS workflow        | Address before production expansion or new finance features |
| P1    | High likelihood of incorrect business state or difficult recovery | Plan in the next engineering milestone                      |
| P2    | Maintainability, reliability, or operational weakness             | Schedule after P0/P1 foundations                            |
| P3    | Quality improvement with limited immediate business risk          | Maintain as backlog work                                    |

| SEC-01  | P0       | Route protection is renderer-only in [`src/renderer/src/App.tsx`](src/renderer/src/App.tsx). MongoDB URIs commonly include credentials.                                                                                                                                                                                                  | Credentials may appear in logs, support bundles, backups, or local disk reads.                                                                                                       | Remove URI logging immediately. Account balances and reports can disagree after corrections or partial failures.                                       | Replace single-entry writes with a journal posting service: at least two entries per posting, debit total equals credit total, immutable posted journals, and explicit reversal journals. Derive balances from postings or update cached balances only in the same transaction.        | The schema/service rejects unbalanced journals; each sale, payment, refund, expense, and supplier payment produces a balanced journal; reconciliation tests pass.                        |
| INV-01  | P1       | Stock is changed in multiple handlers and product modes are implemented in [`Product.ts`](src/main/models/Product.ts), [`inventory.handler.ts`](src/main/ipc/handlers/inventory.handler.ts), [`sales.handler.ts`](src/main/ipc/handlers/sales.handler.ts), and [`purchase-orders.handler.ts`](src/main/ipc/handlers/purchase-orders.handler.ts). The primary workflow does not use the existing `ProductStock`/`StockTransaction` models consistently. | Concurrent sale/restock/refund operations can oversell or cause drift. SIMPLE, RAW_MATERIAL, and COMBO_SET rules may diverge across paths.                                           | Make an append-only stock movement service the single writer. Use conditional updates/versioning or transactions to prevent negative stock. Calculate or reserve composite stock consistently from component movements.                                                                | Every inventory change creates one stock movement with reference ID; attempted oversell is rejected; refunds and PO receiving are idempotent and covered by tests for all product kinds. |
| VAL-01  | P1       | Renderer forms use Zod, but IPC handlers generally accept untyped `data` directly, e.g. [`auth.handler.ts`](src/main/ipc/handlers/auth.handler.ts), [`inventory.handler.ts`](src/main/ipc/handlers/inventory.handler.ts), and [`sales.handler.ts`](src/main/ipc/handlers/sales.handler.ts).                                                                                                                                                            | Renderer validation can be bypassed; unsafe types, invalid ObjectIds, negative amounts, and unexpected fields may reach the database.                                                | Move shared schemas into a neutral contracts module usable by preload/main/renderer. ## Cross-Cutting Design Gaps

| Area           | Current shape                                                                    | Why it becomes a problem                                | Target shape                                                              |
| -------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------- |
| Trust boundary | Renderer picks IDs/store and invokes exposed IPC methods                         | UI checks are bypassable and do not establish authority | Main process owns session identity and policy checks                      |
| Domain logic   | Large IPC handlers combine parsing, authorization, persistence, and side effects | Hard to test, reuse, transact, and audit                | Thin IPC adapters call validated domain services                          |
| Money movement | Sale/payment/expense flows create independent records                            | Accounting and business records can diverge             | One transactional posting workflow per business event                     |
| Inventory      | Product balance is mutated through several paths                                 | High risk of stock drift and overselling                | Immutable stock movements plus concurrency control                        |
| API contract   | Preload methods and declaration types are hand-maintained                        | Silent mismatch across three processes                  | Shared typed command contracts                                            |
| Operations     | Local config and MongoDB are relied on directly                                  | Hard to deploy, recover, upgrade, and support           | Managed configuration, migration, backup, diagnostics, and release checks |

## Minimum Test Matrix Before Further Financial Features

| Scenario                         | Assertions                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Create a cash sale               | Invoice, stock movement, cash journal, account balance, and audit event commit together                |
| Create a credit sale             | Customer balance and receivable journal are correct; no cash movement is posted                        |
| Partially pay a sale             | Paid amount/status/customer balance/account entry update exactly once                                  |
| Refund paid and credit sales     | Refund cap is enforced; stock and financial reversal are correct; duplicate refund command is harmless |
| Receive/cancel a purchase order  | Stock and supplier liability update only for valid status transitions                                  |
| Concurrent sale of last unit     | At most one sale succeeds; stock never goes negative                                                   |
| Unauthorized IPC call            | Cross-store, admin-only, and caller-supplied user ID attempts are rejected                             |
| Failed mid-workflow write        | No partial stock, balance, sale, transaction, or audit records remain                                  |
| Database reconnect/config update | New valid configuration reconnects; invalid URI leaves the current working connection intact           |
| Backup/restore                   | Restored data passes key report and reconciliation checks                                              |

## Notes on Scope

- This report does not claim a live exploit, a production outage, or financial data corruption. It identifies code paths where the required control is absent or cannot be demonstrated from static review.
- The existing `ActivityLog`, `ProductStock`, and `StockTransaction` models are useful foundations, but they must become part of the primary write path to provide control value.
- The report deliberately prioritizes correctness and authorization ahead of visual/UI improvements. In a POS, an attractive feature that can misstate money or stock is a production liability.
